# 上游检查定义

执行入口：本任务的每日检查自动化（每天 10:00），或手动运行 `tools/update_backend.py <固定提交>`。

## 比较对象

- 源：`Kizzuwatnaa/DLSS5-Autopilot` 的正式 Release，排除草稿和预发布。
- 基线：`backend-version.json` 中的提交，不以本地分支 HEAD 代替。
- 评估记录：`docs/UPSTREAM-<版本>.zh-CN.md`。已经评估但尚未接入的版本仍须完成接入，不能因已有报告而跳过。
- 新标签先解析成完整提交；检查和后续应用都针对该提交，避免检查后标签移动。

## 每次必须检查

| 项目 | 输出要求 |
| --- | --- |
| 差异范围 | 标签、提交、变化文件、Release 说明和实际代码差异 |
| 接口 | 新增／删除／变更的函数签名、Options 字段、返回结构 |
| 行为 | 默认值、版本选择、安装目标、备份／卸载、扫描证据和预算 |
| 用户操作 | 对比原界面与 CLI，列出需接入 Qt 的控件、提示、确认与清理行为 |
| 依赖 | 下载来源、归档格式、证书、打包资源和第三方许可变化 |
| 安全边界 | 全局层／注册表写入、反作弊、联网范围，不自动实际安装或捕获画面 |
| 验证 | 隔离运行接口、UI、CLI、INI 检查；新增行为需要针对性测试 |
| 结论 | 可直接继承的修复、需适配项、缺少硬件的验证项和建议优先级 |

接口检查通过不等于功能完整。v1.7.2 的 `chosen=True` 和可选 certifi 导入是典型例子：旧调用仍然合法，却没有获得预期修复。

发现正式版本后先 dry-run，随后完成固定提交接入、前端适配、回归、版本递增、构建、提交推送与 CI 验证。检查报告不是交付终点。无需用户逐步催促；确有阻塞时说明具体原因。保留用户修复，不自动安装游戏组件，不改写 README 宣传，不改变仓库可见性或发布 Release。无变化保持安静，交付完成、失败或需要决定时通知。

## 应用更新的条件

完成必要的前端适配、依赖声明及测试后，才允许应用固定提交。保存旧核心与匹配的旧应用构建，更新本产品版本，生成新目录构建；再经过独立 CI 验证。需要真实游戏或设备才能判断的项目必须写明未验证。
